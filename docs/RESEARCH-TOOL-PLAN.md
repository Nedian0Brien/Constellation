## 1. 대상 사용자

모든 단계의 완료 기준이 이 결정에 달려 있어서 가장 먼저 정해야 한다.

- **본인 전용 도구**: 파이프라인은 저장소의 Python 환경에서 실행하고, 키는 `.env`에 두고, 에이전트 서버는 따로 띄운다. 지금 방식을 유지하면서 기능만 늘린다.
- **다른 연구자에게 배포하는 도구**: `.app` 하나로 설치가 끝나야 한다. 이를 위해 다음이 필요하다.
  - 서명과 공증
  - Python 파이프라인과 에이전트 서버를 앱에 묶기
  - OpenAlex·S2 키를 입력하는 화면
  - 빈 DB에서 시작하는 첫 실행 흐름

`docs/PLAN.md`의 비목표 가운데 "로컬 단일 사용자"는 배포하는 경우에도 유지된다. 한 사람이 자기 기기에서 쓰는 도구라는 점은 같기 때문이다. **결정(2026-09-30)**: 당분간 본인 전용으로 만들고, 다른 연구자 배포는 이후 단계에서 한다. 배포 전용 작업은 7절의 "배포" 단계로 모았다.

## 2. 현재 상태 진단

지금의 Constellation은 파이프라인이 만든 분석 결과 하나를 여러 방식으로 보여 주는 뷰어다. 연구 도구가 되려면 다음이 더 있어야 한다.

- **입력**: 사용자가 논문을 넣는 경로
- **저장**: 사용자가 한 작업(선택, 메모, 컬렉션, 보기)을 남기는 저장소
- **전환**: 문서처럼 여러 지도를 열고 오가는 기능
- **추출**: 결과를 논문 목록이나 그림으로 내보내는 기능

Shneiderman의 시각화 과업 가운데 history(작업 이력)와 extract(내보내기)가 비어 있는 상태다. 사용자가 "단일 페이지"라고 느끼는 이유가 이것이다. 저장된 것이 없으니 다시 열어도 같은 화면이고, 가져갈 결과물이 없다.

코드에서 확인한 원인은 다음과 같다.

- 앱의 DuckDB 연결은 읽기 전용이고 API는 GET만 있다(`crates/constellation-core/src/db.rs:35-37`).
- 파이프라인은 CLI로만 실행되고, 수집 쿼리는 `backend/constellation/ingest/queries.py`의 코드 상수다.
- DB 파일 하나가 코퍼스 하나다. 헤더 선택기는 같은 코퍼스 안에서 임베딩 모델을 바꾸는 기능이고, 지도를 바꾸는 기능은 "데이터베이스 열기" 대화상자뿐이다.
- 사용자 상태로 저장되는 것은 패널 열림과 run별 대화 기록뿐이다. 대화 키가 `run_id` 하나라서 다른 DB의 같은 run_id와 섞일 수 있다.
- 논문을 추가하면 새 run이 생기고, 클러스터·트리·이름·흐름·계보를 모두 다시 계산해야 한다. 클러스터링용 10차원 UMAP을 저장하지 않아 클러스터 번호도 실행마다 바뀐다(`analyze/cluster.py:162-166`).

## 3. 제품 방향

경쟁 도구 조사에서 다른 도구가 제공하지 않는 영역이 확인됐다. 조사 범위 안에서 찾지 못했다는 뜻이고, 시장 전체에 없다는 근거는 아니다.

- **로컬 라이브러리 위의 탐색형 지도**: 탐색형 도구(Litmaps, ResearchRabbit, Connected Papers, Inciteful)는 모두 웹 전용이다. 로컬 도구(VOSviewer, CiteSpace, Bibliometrix)는 WoS·Scopus에서 내보낸 파일을 한 번 분석하는 방식이다.
- **1만 편 이상 코퍼스의 의미 지도**: 탐색형 도구가 한 번에 다루는 규모는 수십에서 수백 편이다. 초록 임베딩과 인용 관계를 이 규모에서 한 지도로 보여 주는 연구자용 도구는 이번 조사에서 확인하지 못했다.
- **에이전트의 지도 조작과 시간 재생**: 에이전트가 필터·선택·시점 이동을 실행하는 도구와, 연도가 넘어갈 때마다 해당 연도 논문이 지도에 나타나는 재생 기능은 다른 도구에서 확인하지 못했다.

반대로 연구자가 이런 도구에 기본으로 기대하는 기능은 대부분 없다. DOI·BibTeX·Zotero 가져오기, 여러 지도 관리, 새 논문 알림, BibTeX·RIS·CSV 내보내기가 여기에 해당한다. 이 기획은 빠진 기본 기능을 먼저 구현하고, 위 영역의 기능은 그다음에 강화하는 순서다.

## 4. 객체 모델

사이드바와 기능은 이 객체들을 보여 주고 조작하는 화면이므로, 객체를 먼저 정한다. 이름은 GIS 도구가 프로젝트·레이어·맵 테마를 구분하는 방식을 따랐다.

| 객체 | 정의 | 저장 위치 |
|---|---|---|
| 코퍼스 | 수집 정의와 그 정의로 모은 논문 목록. 논문·저자·인용 원천 데이터는 코퍼스끼리 공유한다 | 분석 DB |
| 지도 | 코퍼스 + 임베딩 모델 + 투영·클러스터링 파라미터로 만든 좌표와 분석 산출물. 지금의 `kind='project'` run과 그 파생 산출물이다 | 분석 DB |
| 레이어 | 같은 지도 좌표 위에 겹쳐 그리는 것: 클러스터 영역, 인용선, 컬렉션 강조, 추가한 논문, 에이전트 주석 | 표시 상태 |
| 저장된 보기 | 레이어 표시 + 필터 + 카메라 + 뷰 모드 + 색 기준 | 사용자 저장소 |
| 선택 집합 | 올가미, 클러스터 클릭, 검색, 인용 이웃, 에이전트 답변이 만드는 논문 id 집합 | 세션, 저장하면 컬렉션 |
| 컬렉션 | 사용자가 이름 붙여 저장한 논문 집합. 한 논문이 여러 컬렉션에 들어간다 | 사용자 저장소 |
| 논문 주석 | 태그, 읽음 상태, 메모, 선별 판정 | 사용자 저장소 |
| 작업 | 수집·추가·재계산처럼 오래 걸리는 파이프라인 실행과 그 진행 상태·로그 | 사용자 저장소 |

좌표가 달라지면 다른 지도다. 논문을 추가해 점이 늘어도 좌표계가 같으면(`UMAP.transform`) 같은 지도의 새 버전이고, 전체 재계산을 하면 새 지도다.

**저장소 분리.** 분석 DB는 파이프라인만 쓰고 앱은 읽는다. 사용자가 만든 것(컬렉션, 주석, 저장된 보기, 작업 기록)은 앱 데이터 폴더의 별도 파일에 둔다. 사용자 데이터의 키는 `(분석 DB 경로, run_id, 논문 id)`로 잡아 DB 사이에서 섞이지 않게 한다. 이렇게 나누면 분석 DB를 다시 만들어도 사용자 작업이 남고, 사용자 조작은 DuckDB의 "쓰기 1개 또는 읽기 여러 개" 제약과 무관하게 저장된다. 사용자 저장소도 DuckDB 파일로 둔다(9절 결정).

## 5. 기능 영역

### 5.1 지도 목록과 전환

- 분석 DB의 코퍼스·지도 테이블이 지도 목록이다. 항목마다 이름, 코퍼스, 논문 수, 생성일, 생성 파라미터 요약을 둔다. 코퍼스끼리 논문을 공유하므로 임베딩 캐시도 공유된다.
- 지도 전환기는 사이드바 맨 위에 둔다. 전환하면 URL 상태(`run`)와 사용자 저장소의 보기가 함께 바뀐다.
- 헤더의 모델 선택기는 지도 전환기에 합친다. 같은 코퍼스를 다른 모델로 만든 run은 별도 지도로 보인다.
- 지도 정보 패널에서 코퍼스 수집 쿼리·날짜·출처, 임베딩 모델, UMAP 파라미터와 시드, 클러스터링 설정을 보여 준다. 이 항목은 PRISMA-S 보고 항목(DB, 검색식, 날짜, 제한 조건)과 맞춘다.
- 대화 기록과 카메라 위치를 지도 단위로 저장한다.

### 5.2 좌측 사이드바

[정보 구조 조사](research/2026-09-30-ia-workflows.md)의 안 A(지도 전환기 + 단일 목록)를 기본으로 권한다. 지금 구조와 가장 가깝고, 맨 위의 지도 전환과 가운데의 레이어가 위치로 구분된다.

- 뷰 전환(연구 지도, 계층 트리, 갈래 흐름, 인용 계보, 3D 별자리)는 사이드바에서 빼서 캔버스 위 세그먼트 컨트롤로 옮긴다. 같은 지도를 다르게 보는 방법이라서 지도 전환과 같은 자리에 두면 헷갈린다.
- 에이전트 채팅은 지금처럼 오른쪽 보조 사이드바에 두고, 현재 선택 집합을 대화 맥락으로 받는다.

사이드바는 두 차례로 나눠 바꾼다. 사이드바는 객체 목록을 보여 주는 자리인데, 컬렉션·주석·저장된 보기는 사용자 저장소가 생긴 뒤에야 존재하기 때문이다.

| 차수 | 구성 | 선행 조건 |
|---|---|---|
| 1차 | 지도 전환기, 검색(⌘K), 레이어 표시, 영역 트리(상위 분야 → 하위 분야 → 클러스터, 편수), 지도 정보 | 지도 목록 |
| 2차 | 추가한 논문, 컬렉션 트리, 태그, 읽음 상태 목록, 저장된 보기, 작업 상태 | 사용자 저장소, 작업 실행기 |

수집과 체계적 리뷰(선별 단계, 제외 사유)가 커지면 안 B의 아이콘 열(지도 · 라이브러리 · 수집 · 리뷰 · 내보내기)을 더한다. 객체 모델을 안 B와 안 C가 쓰는 객체까지 포함해 잡아 두었으므로 이때 데이터 구조는 그대로 쓴다.

### 5.3 논문 직접 추가

입력 경로는 사용 빈도와 구현 비용 순으로 정했다.

1. DOI·arXiv ID·OpenAlex URL 붙여넣기(여러 줄)
2. BibTeX·RIS·CSL-JSON 파일
3. Zotero 로컬 API(`localhost:23119`, 사용자가 Zotero 설정에서 허용해야 함)로 컬렉션 가져오기
4. PDF(DOI 추출, 실패하면 GROBID). GROBID는 Docker가 필요해 후순위다.

처리 순서는 다음과 같다.
1. **식별자 해석**: DOI는 OpenAlex 단건 조회(무료)로 해석한다. OpenAlex works에는 arXiv 식별자가 없으므로 arXiv ID와 OpenAlex에서 찾지 못한 DOI는 Semantic Scholar `/paper/batch`로 해석해 OpenAlex에 다시 맞춘다.
2. **초록 확보**: OpenAlex, S2, arXiv, Crossref 순으로 찾는다. 모두 실패하면 제목만으로 임베딩하고 품질 표시를 붙인다.
3. **지도에 배치**: 저장된 모델로 임베딩 → `UMAP.transform` → HDBSCAN `approximate_predict`로 기존 클러스터에 배정한다.
4. **인용 연결**: OpenAlex `referenced_works`로 기존 논문과 연결한다.

추가한 논문은 "추가한 논문" 레이어로 따로 강조하고, 어느 클러스터에 들어갔는지 알려 준다. 코퍼스 밖 논문이라 지도에 넣지 않고 목록에만 둘지 사용자가 고를 수 있게 한다.

**증분 배치가 되려면 파이프라인 선행 수정이 필요하다.**
- 클러스터링용 10차원 UMAP 모델을 저장한다.
- `sklearn.cluster.HDBSCAN`을 `hdbscan` 패키지로 바꾸고 `prediction_data=True`로 학습한다. sklearn 구현에는 예측 메서드가 없다.
- project 단계가 새 run을 만드는 대신 기존 run에 점을 더하는 모드를 만든다.
- 각 단계가 "최신 run"을 암묵적으로 고르는 대신 `--run`으로 대상을 받는다.

증분으로 넣을 수 있는 것은 좌표와 클러스터 배정까지다. 계층 트리, 영역 이름, 갈래 흐름, 인용 계보는 전체 재계산 때 갱신된다. 전체 재계산을 제안할 기준은 아래와 같다. 이 기준은 이 기획의 제안이고, 공식 문서에 수치 기준은 없다.
- 새 점이 기존 점의 10–20%를 넘는다.
- 새 점 가운데 노이즈로 배정된 비율이 기존 노이즈 비율보다 뚜렷하게 높다.
- 새 분야를 추가했거나 임베딩 모델을 바꿨다.

### 5.4 분야 수집

- 수집 쿼리를 코드 상수에서 사용자 정의 설정(파일 또는 사용자 저장소)으로 옮긴다. 기존 수집 세트는 기본 제공 예시로 남긴다.
- 분야는 OpenAlex 토픽 체계(도메인 → 필드 → 서브필드 → 토픽)에서 고르고, 키워드 검색식을 더할 수 있다. 여기에 게재 연도 범위와 최소 피인용 수 필터를 붙인다.
  - `primary_topic` 기준은 좁고 정밀하다.
  - `topics` 기준은 넓다.
  - 토픽이 붙지 않은 논문(약 12%)은 키워드 검색과 인용 확장으로 보완한다.
- 실행 전에 예상 편수와 API 비용을 보여 준다. 1만 편 수집은 list 호출 100회, 약 $0.01이다. 무료 키 한도는 하루 $1이다.
- 실행하면 작업 실행기가 collect → embed → project → cluster → hierarchy → name → flow → lineage를 차례로 돌리고, 단계별 진행률과 로그를 보여 주며, 취소할 수 있다. 결과는 새 지도로 목록에 들어간다.
- 수집 결과를 선별하는 기능을 둔다. 주제 밖 논문을 제외 표시하고 다시 계산할 수 있어야 한다. 피지컬 AI 코퍼스에서 수집어가 다른 분야와 겹쳐 주제 밖 논문이 섞인 사례가 있다(`docs/PHYSICAL-AI-RESULTS.md:91-102`).
- 영역 이름 짓기는 codex·claude CLI 로그인에 의존한다. 로그인이 없으면 c-TF-IDF 라벨로 대신하고, 나중에 이름 짓기만 다시 실행하게 한다.

### 5.5 개인 지식 기능

- **선택 집합**: 올가미 선택을 새로 만들고, 클러스터 클릭·검색 결과·인용 이웃·에이전트 답변과 같은 집합으로 다룬다. 선택 집합에서 할 수 있는 동작은 다음과 같다.
  - 컬렉션 저장
  - 태그
  - 하위 지도 만들기(선택한 논문만으로 다시 투영)
  - 에이전트에게 요약 요청
  - 내보내기
- **컬렉션**: 한 논문이 여러 컬렉션에 들어간다. 지도에서 컬렉션을 레이어로 켜면 위치가 강조된다.
- **논문 주석**: 태그, 읽음 상태(안 읽음 · 읽는 중 · 읽음), 메모. Zotero는 읽음 상태를 기본 기능으로 두지 않아 플러그인으로 해결하는데, 사용자 요청이 오래 쌓인 기능이다.
- **저장된 보기**: 레이어·필터·카메라·뷰 모드를 이름 붙여 저장하고 다시 연다.
- **영역 이름 수정**: 사용자가 이름을 고치면 `label_src='manual'`로 남겨 재계산 때 보존한다. 스키마 주석에만 있고 쓰는 코드가 없는 값이다.

### 5.6 내보내기와 재현성

- 논문 목록 내보내기: BibTeX, RIS, CSV, CSL-JSON. 단위는 선택 집합, 컬렉션, 필터 결과.
- 그림 내보내기: 현재 화면을 PNG·SVG로 저장. 지도 정보(코퍼스, 모델, 날짜)를 캡션으로 넣는 옵션을 둔다.
- 지도 스냅샷: 좌표, 클러스터, 논문 id 목록, 생성 파라미터, 수집 쿼리를 한 묶음으로 내보낸다. Zenodo에 올리면 버전별 DOI로 인용할 수 있다.
- 재현성 기록: UMAP은 `random_state`를 지정해야 재현된다. 모든 지도의 파라미터와 시드를 `runs.params_json`에 남기고 지도 정보 패널에서 보여 준다.
- Zotero로 내보내기: 컬렉션을 Zotero로 보낸다. Zotero 로컬 API의 쓰기는 Zotero 10 이상에서 로컬 키가 필요하다. 그 전에는 BibTeX 파일로 대신한다.

### 5.7 새 논문 모니터링

지도나 컬렉션 단위로 새 논문을 확인한다.
- **OpenAlex 무료 경로**: 게재일 기준으로 최근 기간을 다시 조회하고 로컬에서 중복을 뺀다. `from_updated_date` 필터는 유료 플랜 전용이다.
- **arXiv 카테고리 RSS**: 보조 수단으로 쓴다.
- 새 논문은 "받은 논문" 목록에 모았다가, 사용자가 고른 것만 5.3의 증분 배치로 넣는다.

`docs/PLAN.md`의 비목표 "실시간 자동 갱신 — 수집은 명시적 실행"을 바꾸는 항목이다. 자동 실행 대신 앱을 열 때 확인하거나 사용자가 누를 때 확인하는 방식으로 두면 비목표의 취지(예상하지 못한 데이터 변경 방지)는 지킬 수 있다.

### 5.8 에이전트

- 새 도구를 더한다.
  - 선택 집합과 컬렉션을 다루는 도구: 만들기, 추가, 태그
  - 가져오기 후보를 제안하는 도구: DOI 목록을 받아 추가 대기열에 넣기
- 대기열에 들어간 논문은 사용자가 확인한 뒤에 추가한다.
- 배포하는 경우 에이전트 서버(Node)를 앱에 묶어야 한다. 지금은 따로 띄워야 한다(README:49).

## 6. 기반 작업

### 6.1 작업 실행기

수집·추가·재계산을 앱에서 실행하고, 진행률·로그·취소를 제공하는 모듈이다. Tauri가 파이프라인 프로세스를 띄우고 표준 출력의 진행 이벤트를 웹뷰로 전달한다. Tauri shell 또는 sidecar 플러그인과 그 권한 설정이 새로 필요하다.

파이프라인이 분석 DB에 쓰는 동안에는 앱의 읽기 연결과 충돌한다. 해결 방법은 다음과 같다.
- 쓰기 동안 앱이 연결을 닫는다. 그 사이 화면은 이전 데이터를 캐시로 보여 준다.
- 새 run을 임시 파일에 만든 뒤 교체한다.

두 번째가 사용 중 끊김이 없지만 구현이 크다. 어느 쪽으로 할지는 작업 실행기 spec에서 정한다.

### 6.2 파이프라인 실행 방식

**결정(2026-09-30)**: 지금은 로컬 Python 환경(저장소 `.venv`)을 앱이 호출한다. 배포 단계에서 런타임 번들로 바꾼다. 아래 표는 그때 다시 볼 선택지다.

| 방식 | 내용 | 비용 | 제약 |
|---|---|---|---|
| 로컬 Python 환경 요구 | 사용자가 uv 등으로 환경을 설치하고 앱이 그 경로를 호출 | 가장 작다 | 배포 대상 연구자의 설치 부담. 본인 전용이면 충분하다 |
| 런타임 번들 | Python 런타임과 의존성(torch 포함)을 앱에 묶어 sidecar로 실행 | 패키징·서명 작업이 크고 앱 크기가 크게 늘어난다(크기 미측정) | 앱 업데이트 크기, 공증 대상 바이너리 증가 |
| 핵심 경로 이식 | 임베딩 추론(ONNX 등), UMAP transform, 클러스터 배정만 Rust로 옮기고 전체 재계산은 Python에 남김 | 이식과 결과 동등성 검증이 크다 | 전체 재계산은 여전히 Python 필요 |

### 6.3 비밀 값

OpenAlex·S2 키를 앱 설정 화면에서 입력받아 macOS 키체인에 저장한다. 파이프라인에는 환경 변수로 넘긴다. 본인 전용이면 `.env`를 계속 써도 된다.

## 7. 단계별 로드맵

핵심 흐름은 **새 지도 만들기**다. 사용자가 분야나 시드 논문으로 새 지도를 정의하면, 파이프라인이 수집부터 별자리 지도 완성까지 자동으로 실행한다. 사용자는 완성된 지도에 원하는 논문을 직접 추가한다(2026-09-30 방향 결정). 각 단계는 `.intent/` 절차의 intent 하나 이상이다.

| 단계 | 내용 | 선행 | 사용자에게 보이는 결과 |
|---|---|---|---|
| 1 | 코퍼스·지도 데이터 모델: 분석 DB 하나에 코퍼스 테이블, 파이프라인의 대상 지도 명시(`--map`), 지도별 투영 모델 저장, 기존 DB 통합, 헤더 선택기를 지도 선택기로 | — | 한 앱 안에서 RAG/IR 지도와 피지컬 AI 지도를 오간다 |
| 2 | 새 지도 만들기: 작업 실행기(앱이 로컬 Python 파이프라인 실행, 진행률·로그·취소), 수집 정의(OpenAlex 분야·키워드, Zotero 컬렉션, DOI 목록), 전 단계 자동 실행 | 1 | 앱에서 새 분야 지도를 만든다 |
| 3 | 지도에 논문 추가: DOI·arXiv·BibTeX·RIS·Zotero, 증분 배치(UMAP10 저장, `hdbscan` 교체), 추가한 논문 레이어 | 1, 2 | 내 논문을 지도에 넣고 위치를 확인한다 |
| 4 | 사이드바 개편과 사용자 저장소: 지도 전환기, 레이어, 영역 트리, 지도 정보, 뷰 세그먼트 컨트롤, 지도 단위 대화·카메라 저장 | 1 | 사이드바에서 지도와 분야 계층을 탐색한다 |
| 5 | 선택 집합, 컬렉션, 태그·읽음·메모, 저장된 보기, 영역 이름 수정, 내보내기 | 4 | 작업을 남기고 BibTeX·그림으로 가져간다 |
| 6 | 모니터링, 에이전트 도구 확장, 체계적 리뷰(선별 판정·PRISMA 건수) | 3, 5 | 새 논문을 받아 보고 리뷰 절차를 앱 안에서 진행한다 |
| 배포 | 런타임 번들, 에이전트 서버 번들, 키 입력(키체인), 첫 실행, 서명·공증 | 2 | 다른 연구자가 설치해 쓴다 |

4단계는 1단계 뒤 아무 때나 2·3단계와 병행할 수 있다.
